## 1. 总体流程（已确认）

```text
用户 → Project Copilot：确认需求、明确参数、拆任务、写 Brief
     → Task Orchestrator：并行派发、计时、重试、记账
     → Lab / Research / Procurement Specialist：各自独立完成，交回 Artifact
     → 规则校验（确定性代码）：通过 / 不通过 / 未知
     → Project Copilot：汇总成 InstrumentPlan
```

整个过程中，每一步都带同一个运行 ID，可以按这个 ID 串起全链路。

## 2. 已做的决定

### A1 记忆分层（2026-11-06 确认）

| 层 | 内容 | 存在哪里 | 是否跨项目 |
|---|---|---|---|
| 项目记忆 | 需求版本、结论、证据、方案、测试结果 | 业务数据库（Project Service） | 否 |
| 跨项目知识 | **实验室知识**（内部文档、复盘、规范）+ **经验记忆**（从项目中总结的经验） | 同一个知识库，条目带类型标签加以区分 | 是 |
| 工作记忆 | 单次运行的中间步骤、草稿 | 运行状态（用完可清） | 否 |

- 项目记忆与跨项目知识严格分开。
- Agent 自己“记住”的内容不能当作事实，使用前必须重新查证；只有业务数据库里带证据的记录才是事实。
- 本文中的“**经验库**”指知识库中类型为“经验”的那部分条目，**不是一个单独的库**；它与实验室知识共用同一套存储和检索，只在类型标签、审核流程和遗忘规则上不同。

### A2 经验记忆走晋升池（2026-11-06 确认）

经验不直接写入知识库，必须经过以下流程，**每一步都在页面上可见**：

```text
触发事件 → 候选经验 → 晋升池（自动去重、检测冲突）→ 人工审核 → 经验库（知识库中的经验条目）
```

**触发事件**：只在以下事件发生时产生候选经验，不是每次运行都产生。

| 事件 | 例子 | 依赖的业务记录 | 最早可用阶段 |
|---|---|---|---|
| 用户纠正了某个结论 | “SPEC-C 其实没有制冷” | `UserCorrection`（P1 定义） | P3（通过命令行纠正），P5 起可在页面上纠正 |
| 用户回答了 Copilot 的提问 | “我们优先选有 Python SDK 的厂商” | `UserQuestion`（P1 定义） | P3 |
| 同一类问题反复出现 | Vendor Gamma 的参数页在三个项目中都缺字段 | 按规则统计 Claim 中的未知值：同一厂商、同一参数在**至少 3 个不同项目**中为未知。同一项目的多次运行只算 1 次；基准任务项目（`InstrumentProject.kind = benchmark`）默认不计数 | P3 |
| 项目结束时的复盘 | Copilot 汇总整个项目，起草几条经验 | 项目的全部业务记录 | P3 |
| 测试失败 | 实测分辨率比标称差 20% | `TestResult`（P1 定义，P7 使用） | P7 |

“反复出现”按项目计数，而不是按运行计数，原因是：基准任务中本来就应当为未知的参数（如 SPEC-C 的制冷温度），在可重复性测试中会被连续运行 N 次；同一项目重跑几次也只是同一个事实的重复观察。按运行计数会不断产生无意义的候选经验。

**候选经验的内容**：一句话的经验陈述；适用范围（某厂商 / 某类器件 / 某种测量 / 通用）；类型（事实型 / 方法型 / 偏好型）；证据（项目、运行、结论，必须可追溯）；支持次数。

**晋升池的自动处理**：

1. 去重：先用向量相似度（pgvector）找相近条目，再由模型判断新旧两条的关系：相同（合并，支持次数加 1）/ 更具体（作为补充）/ 矛盾（标记冲突）/ 无关（新条目）。
2. 冲突：不自动覆盖，交给人裁决；默认以实验室文档为准，经验不能覆盖人写的文档。

**人工审核**：V1 所有晋升都由人审核，可以通过、驳回或修改后通过。审核时记录支持次数、冲突情况、来源，作为以后制定自动晋升规则的数据。

**可视化**（因为数据量小，每一条经验都应当能被看清）：

- 事件流：发生了哪些触发事件，各自产生了哪些候选经验
- 候选经验卡片：内容、来源事件、原始证据链接
- 晋升池状态：被合并到哪一条、与哪一条冲突、等待审核
- 经验库：每条经验的支持次数、被检索和被采用的次数、综合评分、评分成熟度、生命周期与有效性状态（C2）

**使用规则**：Agent 检索到经验时只能当作线索，必须重新查证后才能写进结论（A1）。

**分阶段实现**：

| 阶段 | 内容 |
|---|---|
| P2 | 写进 Agent 架构设计文档 |
| P3 | 记录前 4 类触发事件（测试失败要到 P7）并生成候选经验；只读查看页面展示事件流和候选经验 |
| P4 | 晋升池的去重与冲突检测；经验条目的存储与检索，与实验室知识共用 pgvector；按 C2 实现评分、历史、有效性和自动生命周期管理（P5 审核通过后才对 Agent 可见） |
| P5 | 审核页面（通过 / 驳回 / 修改）、经验库页面；按 C2 展示评分并提供人工管理 |
| P7 | 按 C2 将 TestResult 纳入使用效果评分，离线校准权重和阈值；自动晋升仍需另行决策 |

经验评分与生命周期管理已确认，具体规则及分阶段实现见 C2。

### A8 失败案例转为考题（2026-11-06 确认方向）

除了沉淀为经验，每一个**确认过的错误**（用户纠正、测试失败、回归中发现的问题）都应当转成基准任务包里的一道新题：

```text
确认的错误 ─┬→ 候选经验 → 晋升池 → 经验库（下次希望 Agent 记得）
            └→ 新考题 → 加入基准任务包 → 之后每次修改技能或提示词都必须通过（保证不再犯）
```

- 这是数据量小的团队最有效的改进方式：考卷越积越厚，比数据越积越多更可靠。
- 新考题按基准任务包的修改规则发布新版本，不修改已用于验收的旧版本。
- 是否转成考题、如何出题，由人决定；系统负责把失败案例和它的 trace 一起整理出来。

### A3 Specialist 之间不直接沟通（2026-11-06 确认）

- 所有协作都经过 Copilot。
- **Copilot 在下发 Brief 之前，就要把参数分成两类：**
  - **指定参数**：需求明确要求的，带需求项编号、目标值和单位，例如 R04 激光功率 ≥ 450 mW。
  - **不定参数**：需求没有要求的，Specialist 可以自由选择，但需要报告实际值。
- 遇到缺参数的情况，Specialist 不去找其他 Specialist，而是**多列几个候选**，把每个候选的已知值和未知值都列清楚，交给 Copilot 决定。

### A4 Copilot 可以主动向用户提问（2026-11-06 确认）

- 规划过程中，Copilot 遇到需求有歧义、关键参数缺失、候选之间无法取舍时，可以暂停流程并向用户提问。
- 用户的回答作为证据记录下来（证据来源类型为“用户决定”），回答后流程从暂停处继续。
- 运行状态需要支持“等待用户回答”的暂停与恢复，这是 P2 选型的考察项之一。

### A5 没有数据安全限制（2026-11-06 确认）

- 实验室资料可以发送给外部模型 API，不需要本地部署模型。
- 模型供应商的选择（D2）只需考虑效果和成本。

### A6 不允许运行中自我修改（已确认）

- Agent 不能在运行中修改自己的提示词或技能。
- 改进走离线循环：出错 → 按 trace 定位 → 提出修改 → 用基准任务包回归 → 人工批准 → 发布新版本。

### A7 人工确认点（已确认）

| 环节 | 要求 |
|---|---|
| 需求基线 | 由人确认后才开始规划 |
| 方案采纳 | 由人确认 |
| 对外动作（询价、下单、发邮件） | 由人批准，Agent 只起草 |
| 规划中的歧义 | Copilot 可以暂停提问（A4） |

### A9 V1 运行底座与集成策略（2026-11-08 确认）

- 采用 **DeerFlow Backend + MIS 自研 Web UI + MIS 自有业务后端**，技术选择以 [ADR-0002](../adr/0002-agent-runtime-and-integration.md) 为准。
- DeerFlow 负责 Agent Runtime、Supervisor/SubAgent、通用 Context、Skills、Tools、MCP、Docker Sandbox 和 Checkpoint；MIS 业务 Agent 通过 Lead Agent / SubAgents 执行，Specialist 之间仍不直接通信。
- P2 是 DeerFlow Integration Spike，不再要求两个框架完整对比；关键门槛失败才启动替代评估，替换前必须由负责人确认并修订 ADR-0002。
- 不直接修改 DeerFlow 核心执行引擎，优先官方扩展接口和 Adapter；锁定 release / 完整 commit、依赖、镜像和配置，具体基线在 P2 开始前登记。
- PostgreSQL 独立 runtime schema、人工暂停恢复、结构化产物、Sandbox 文件/网络/资源隔离均须 P2 验证，不能把选型已确认当作验收已通过。

### A10 前后端解耦与业务所有权（2026-11-08 确认）

- MIS Frontend 完全自研 React + TypeScript，不使用、不 Fork DeerFlow Next.js 前端。
- 前端只通过 MIS Backend / BFF 的 REST / SSE 交互，不直连 DeerFlow，也不以其原生 Thread / Run / 事件格式作为产品契约。
- MIS Backend 负责 Business API、Project Service、DeerFlow Adapter、Context Builder、Memory Service、Evolution Service 和权限；Adapter 封装上游调用、ID 映射、事件转换、错误与暂停恢复。
- MIS 独立管理 PostgreSQL + pgvector 中的项目、记忆、证据、产物和 Trace；运行层不能直接修改业务主数据，必须经 MIS 服务校验写入，数据库权限沿用 ADR-0001。
- Runtime 替换限于 Adapter 和相关执行接口的绑定；不能因此重写 MIS 产品契约或迁移业务事实到上游状态库。P2 最小接入、P3 只读页、P5 正式 UI 的阶段边界不变。

### A11 Context、Memory 与 Evolution 接口边界（2026-11-08 确认）

- MIS Context Builder 收敛为轻量 Business Context Assembler：按项目/角色授权选择 Brief、需求、Evidence 与已审核记忆引用；DeerFlow 原生 SubAgent 隔离、摘要压缩、文件卸载和 Middleware 承担通用 Context 运行管理，不另建压缩引擎。
- MIS Memory Service 的三层边界不变：项目事实通过 Project Service，跨项目知识/经验遵循 A1/A2/C2，工作记忆由 Runtime Checkpoint 管理。DeerMem 事实抽取、近重复检测、可选整合和检索是**优先复用候选**，须在 P2 验证可否无正式库写入地独立使用。
- 原生 MemoryMiddleware 对正式记忆的自动写入/读回和隐藏注入先禁用或隔离，但这不等于废弃 DeerMem 通用算法；所有候选按 A2 触发/审核，原生 staleness 不取代 C2。
- 记忆被召回、选中、注入、实际应用及结果通过 C2 结构化事件区分；经验只能作为待查证线索，未经 P5 人工审核不得对 Agent 可见。
- MIS Evolution Service 负责 Trace / 错误整理、经验候选、考题与改进草案；按 A6/A8 离线回归、人工批准后发布，禁止运行中自行修改 Prompt、Skill、评分权重或阈值。
- 以上是后续实现边界，不扩大 P1 核心数据契约范围；P2 先以固定样例/模拟服务验证接入，C1/C2 的正式落地仍按原阶段安排。

## 3. 已有方向、待细化

### B1 上下文（Context）

**V1 最小复用原则**：先沿用 DeerFlow 原生隔离、摘要压缩、文件卸载，只增加业务 Brief 的范围筛选；P2 测试跨项目/角色隔离、摘要后硬约束与 Evidence ID 不丢。

| 角色 | 能看到的 | 看不到的 |
|---|---|---|
| Copilot | 需求、各 Artifact 的结论摘要、未解决的缺口、项目历史摘要 | Specialist 的搜索过程和原始网页 |
| Specialist | 自己的 Brief、相关需求项、自己的技能、本次工具结果 | 其他 Specialist 的工作、整个项目的历史 |

- 长内容（PDF、整页参数）不直接放进上下文，先存为文件或证据，上下文中只放摘要和引用编号，需要时再读取。

### B2 技能（Skills）

- 技能 = 操作说明 + 确定性工具 + 测试用例。
- 带版本号；每个 Specialist 只能使用分配给它的技能。
- Artifact 记录所用技能的版本。

## 4. 已确认的补充架构决策

### C1 Trace 可观测性架构

2026-11-08 正式确认。

#### A. 设计目标

Trace 需要回答三个问题：Agent 做了什么？Agent 为什么这么做？Agent 最终产生了什么结果？通过实际输入、上下文、工具与规则结果及业务结论追溯执行依据。

| 对象 | 职责 |
|---|---|
| Trace | 记录执行过程 |
| Evidence | 记录可追溯的事实和原始证据 |
| Artifact | 记录 Agent 产生的结构化业务结论 |
| InstrumentPlan | 记录最终仪器设计方案 |

四者通过 `run_id`、`trace_id` 和相关业务 ID 关联，不相互替代。

#### B. 三级 Trace 数据结构

**L1：执行骨架（Skeleton，永久保留）**

- Run、Task、Step、Span 的层级关系；`trace_id`、`span_id`、`parent_span_id`。
- Agent、Specialist、`actor`、`task_type`；模型供应商、模型名称和版本。
- Prompt 和 Skill 的不可变版本及 Hash。
- 开始时间、结束时间、耗时；输入 Token、输出 Token、费用。
- 工具调用名称、调用状态、重试次数；成功、失败、超时、异常信息。
- 输入输出内容 Hash 和内容引用 `content_ref`。

**L2：执行内容（Payload，按运行类型保留）**

- LLM 实际接收的动态消息和上下文快照；LLM 原始输出。
- Tool 调用参数及返回结果。
- RAG 检索 Query、命中文档和片段引用。
- Memory 检索结果、选中条目、注入上下文的记忆 ID。
- Rule Engine 的输入、规则版本和判断结果。
- 用户提问、回答和纠正内容。

静态 Prompt 和 Skill 内容通过不可变版本及 Hash 引用，不重复存储相同内容；动态组装的模型输入在对应保留期内必须能够还原。已经作为 Evidence 或原始文件保存的内容优先引用，不重复存储。

**L3：业务结果与证据**

通过业务数据库保存 `AgentArtifact`、`Evidence`、`InstrumentPlan`、`UserCorrection`、`TestResult`、`RequirementBaseline` 版本及其他业务状态变更。Trace 通过 ID 关联这些记录，不复制另一套业务主数据。

#### C. Trace 采集粒度

采用 **OpenTelemetry Trace + GenAI Semantic Conventions**。

```text
Run
 ├── Task
 │    ├── Agent Span
 │    │    ├── LLM Call Span
 │    │    ├── Tool Call Span
 │    │    ├── RAG Retrieval Span
 │    │    ├── Memory Retrieval Span
 │    │    ├── Rule Validation Span
 │    │    └── Artifact Generation Span
 │    └── Human Interaction Span
 └── Other Tasks
```

关键业务事件包括：Agent 开始和结束任务；LLM 和 Tool 调用；RAG 检索；Memory 检索和使用；Rule Engine 校验；人工提问、回答、暂停与恢复；Artifact 生成及状态变化；重试、超时和异常。

只记录具有业务意义的执行边界，不需要给每个 Python 函数建立 Span。**V1 对上述关键事件 100% 采集，不进行采样。**

#### D. 数据存储

- 使用 PostgreSQL 独立的 `trace` schema，骨架与完整内容分表存储。
- 大段内容使用 Hash 去重，通过 `content_ref` 关联。
- Trace 与业务记录、Agent Runtime 状态分离。
- 后续可以接入 Langfuse 等第三方可观测平台，不改变 MIS 自身的业务数据契约。

#### E. 数据保留策略

| 运行类型 | 骨架 | 完整内容 |
|---|---|---|
| 基准测试运行 | 永久 | 永久 |
| 被人工确认的错误案例 | 永久 | 永久 |
| 普通项目运行 | 永久 | 90 天 |

普通运行超过 90 天后删除完整输入输出内容，保留执行骨架、Hash 和业务引用。只有被人工确认的错误案例才进入错误案例永久保留范围，不是所有失败运行都自动永久保留。

Hash 去重内容清理必须考虑共享引用：仍被永久保留或未过期运行引用的 Payload 不得删除；到期运行的 Payload 关联按策略清理。Evidence 等业务记录按业务规则保留，不因 Trace 到期而删除。

#### F. 安全与边界

- 完整输入输出写入前，必须对 API Key、Authorization Header 等凭据脱敏；异常信息也不得泄露凭据。
- Trace 本身不消耗模型 Token；使用模型分析 Trace 或将历史 Trace 放入上下文才会产生模型费用。
- 历史 Trace 默认不自动注入 Agent 上下文。
- Trace 不是业务事实的来源，业务结论仍必须通过 Evidence 追溯。

### C2 Experience Memory Scoring & Lifecycle Management

2026-11-08 正式确认：经验记忆采用持续评分与生命周期管理。

#### A. 管理范围

只对跨项目知识库中的经验记忆评分。

| 记忆类型 | 管理方式 |
|---|---|
| 项目记忆 | 业务数据库、版本化管理 |
| 实验室知识 | 文档版本管理、人工复核 |
| 经验记忆 | 持续评分、生命周期管理 |
| 工作记忆 | 随运行状态管理 |

实验室原始文档不参与经验评分和自动遗忘。经验仍遵循 A2 晋升审核，P5 人工审核通过后才正式对 Agent 可见，使用前仍需重新查证。

#### B. 综合评分

每条经验维护 0～100 的综合评分和四个 0～100 的分项。

| 维度 | 名称 | 权重 |
|---|---|---:|
| E | Evidence Score：证据可信度 | 30% |
| T | Trigger Score：触发频率 | 20% |
| U | Usage Score：实际使用效果 | 35% |
| H | Human Score：人工评价 | 15% |

```text
Total Score = 0.30 * E
            + 0.20 * T
            + 0.35 * U
            + 0.15 * H
```

权重是 V1 初始参数，必须版本化、可配置；后续通过离线评估和人工批准调整，不允许 Agent 运行时自行修改。

#### C. 四个分项的计算

**E：证据可信度**

根据来源可靠性、可追溯性、独立证据支持和冲突情况评价。初始评分参考：

| 分数 | 参考依据 |
|---|---|
| 90～100 | 可复现实验、官方文档或多个独立来源支持 |
| 70～89 | 出处明确，来源可靠 |
| 40～69 | 间接证据或验证不足 |
| 0～39 | 缺乏可靠依据、证据过期或存在明显问题 |

确认被可靠证据证伪时，必须触发有效性状态处理，不能只降低 E。

**T：触发频率**

只统计经验被选中且实际注入 Agent 上下文的有效触发；普通向量检索召回、仅检索到但没有选中的经验不计入 T。这里的有效触发用于使用评分，与 A2 生成候选经验的触发事件不同。

同一 `memory_id`、同一 `project_id`、同一任务类型，30 天内只计一次有效触发，避免重复运行刷分。统计窗口为最近 180 天，N 为窗口内按上述规则去重后的有效触发次数。

```text
T = 50 + 50 * (1 - exp(-N / 5))
```

没有触发时 T 保持中性分 50，而不是 0。

**U：实际使用效果**

只有经验实际应用到任务（Applied）后才进入效果统计：`success` 为正向样本，`failure` 为负向样本，`unknown` 不参与计算。

正向样本包括确定性规则验证成功、测试成功、用户明确认可等可追溯结果；负向样本包括用户纠正、测试证明错误、可靠证据证明经验不适用。不允许把没有用户反馈自动当作成功。

采用 Beta 平滑，P 为正向样本数，F 为负向样本数；未知样本不进入 P 或 F：

```text
U = 100 * (P + 2) / (P + F + 4)
```

**H：人工评价**

范围为 0～100；新进入经验库且尚未人工评分时默认 50。人工可以定期重新评分，记录评分人、时间、评分和原因，历史人工评分永久保留。人工评分与 Pin、强制归档等管理操作分开。

V1 不使用 LLM-as-Judge 自动决定经验分数，优先使用可追溯事件、规则和人工反馈。

#### D. 评分成熟度

`score_maturity` 为 `insufficient_data` 或 `mature`。只有同时满足以下条件，才允许自动执行评分驱动的生命周期转换：

1. 至少在 3 个不同项目中被有效触发。
2. 至少在 2 个不同项目中产生可评价的使用结果（success / failure）。

样本不足时仍计算和展示评分，但不自动降级。新晋升经验默认进入 Active，并标记为 `insufficient_data`。

#### E. 生命周期

`lifecycle_state`：

| 状态 | 分数展示区间 | 检索策略 |
|---|---|---|
| Active | 70～100 | 正常参与检索 |
| Dormant | 40～69 | 默认不检索，可人工查询 |
| Archived | 0～39 | 退出正常检索，仅保留审计 |

区间用于展示，实际转换使用滞回机制，并以评分成熟度和有效性保护为前提；状态不必与单次分数所在区间相同。

| 当前状态 | 转换条件 | 新状态 |
|---|---|---|
| Active | 连续两次月度评分低于 65 | Dormant |
| Dormant | 连续两次月度评分达到 75 | Active |
| Dormant | 连续三次月度评分低于 35 | Archived |
| Archived | 人工审核通过 | Active 或 Dormant |

Archived 不自动恢复；不允许因单次低分直接降级。

#### F. 有效性状态独立管理

`validity_status`：

| 状态 | 含义与使用限制 |
|---|---|
| valid | 正常有效，再根据生命周期决定是否参与检索 |
| contested | 证据冲突，等待人工审核，暂停默认检索 |
| invalid | 已确认错误或失效，禁止 Agent 使用 |

有效性优先级高于综合评分，被证伪的高分经验也必须停止使用。

#### G. 人工管理与评估节奏

支持人工评分、Pin 置顶、强制降级、强制归档、重新激活、标记失效，以及修改经验并产生新版本。所有操作记录操作人、时间、原因、变更前后分数和状态。

Pin 只豁免评分驱动的自动降级，不豁免证据冲突和失效保护，也不绕过晋升审核。评分事件驱动更新，生命周期每月评估一次；用户纠正、证据冲突、连续失败触发即时复核。即时有效性保护不受样本不足或月度周期限制。

#### H. 不同经验类型的有效期

- 事实型：关注来源时效性，支持 `valid_until` 和到期复核。
- 方法型：主要依据实际使用效果，不设置统一过期时间。
- 偏好型：以最新用户确认为依据，新偏好可以取代旧偏好。

不采用所有经验统一的时间衰减公式。

#### I. 核心数据对象

架构层预留以下三个对象；具体字段细化与数据库设计留到 P2/P4，不加入 P1 核心数据模型范围。经验主数据、结构化使用事件和评分历史保存在 PostgreSQL `knowledge` schema。

| 对象 | 预留内容 |
|---|---|
| ExperienceMemory | `memory_id`、`content`、`memory_type`、`scope`、`evidence_refs`；`total_score`；`evidence_score`、`trigger_score`、`usage_score`、`human_score`；`lifecycle_state`、`validity_status`；`score_maturity`、`is_pinned`；`score_version`、`updated_at`；事实型经验的 `valid_until` |
| MemoryUsageEvent | `event_id`、`memory_id`；`run_id`、`trace_id`、`span_id`、`project_id`、`task_id`、`task_type`（用于有效触发去重）；`stage`：retrieved / selected / injected / applied；`outcome`：success / failure / unknown；`artifact_id`、`evidence_id`、`created_at` |
| MemoryScoreHistory | `memory_id`；变更前后总分及四个分项分数；`score_version`；变更原因；`source_event_ids`；`evaluator`；`created_at` |

Trace 记录详细执行过程，MemoryUsageEvent 记录供评分使用的结构化业务事件；二者通过 `trace_id`、`span_id` 关联，不相互替代。评分版本、事件来源、人工评价和状态操作历史共同支持审计。
