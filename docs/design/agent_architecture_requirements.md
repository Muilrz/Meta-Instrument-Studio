## 1. 总体流程（已确认）

```text
用户 → Project Copilot：确认需求、明确参数、拆任务、写 Brief
     → Task Orchestrator：并行派发、计时、重试、记账
     → Lab / Research / Procurement Specialist：各自独立完成，交回 Artifact
     → 规则校验（确定性代码）：通过 / 不通过 / 未知
     → Project Copilot：汇总成 InstrumentPlan
```

整个过程中，每一步都带同一个运行 ID，可以按这个 ID 串起全链路。

## 2. 已做的决定

### A1 记忆分层（2026-11-06 确认）

| 层 | 内容 | 存在哪里 | 是否跨项目 |
|---|---|---|---|
| 项目记忆 | 需求版本、结论、证据、方案、测试结果 | 业务数据库（Project Service） | 否 |
| 跨项目知识 | **实验室知识**（内部文档、复盘、规范）+ **经验记忆**（从项目中总结的经验） | 同一个知识库，条目带类型标签加以区分 | 是 |
| 工作记忆 | 单次运行的中间步骤、草稿 | 运行状态（用完可清） | 否 |

- 项目记忆与跨项目知识严格分开。
- Agent 自己“记住”的内容不能当作事实，使用前必须重新查证；只有业务数据库里带证据的记录才是事实。

### A2 经验记忆走晋升池（2026-11-06 确认方向，细节待定）

经验不直接写入知识库，而是先进入**晋升池**：

```text
项目中产生的候选经验 → 晋升池
  → 去重：与已有经验合并
  → 冲突处理：与已有经验或实验室知识矛盾时，标记出来，不自动覆盖
  → 晋升：进入知识库，成为经验记忆
  → 定期遗忘：长期未被使用、已过时或被推翻的经验降级或移除
```

待讨论：

- 候选经验由谁提出：Copilot 在项目结束时总结，还是每次运行后都可以提出？
- 晋升是否需要人工审核，还是满足一定条件后自动晋升？
- 去重和冲突检测的方法：语义相似度、规则，还是交给模型判断？
- 遗忘的依据：时间、使用频率、被推翻的次数？遗忘是彻底删除还是归档？
- 遗忘是否只针对经验记忆，实验室文档是否也需要过期机制？
- 实现阶段：需要有真实项目产出经验才能验证，建议设计在 P2 完成，实现放在 P3 之后。

### A3 Specialist 之间不直接沟通（2026-11-06 确认）

- 所有协作都经过 Copilot。
- **Copilot 在下发 Brief 之前，就要把参数分成两类：**
  - **指定参数**：需求明确要求的，带需求项编号、目标值和单位，例如 R04 激光功率 ≥ 450 mW。
  - **不定参数**：需求没有要求的，Specialist 可以自由选择，但需要报告实际值。
- 遇到缺参数的情况，Specialist 不去找其他 Specialist，而是**多列几个候选**，把每个候选的已知值和未知值都列清楚，交给 Copilot 决定。

### A4 Copilot 可以主动向用户提问（2026-11-06 确认）

- 规划过程中，Copilot 遇到需求有歧义、关键参数缺失、候选之间无法取舍时，可以暂停流程并向用户提问。
- 用户的回答作为证据记录下来（证据来源类型为“用户决定”），回答后流程从暂停处继续。
- 运行状态需要支持“等待用户回答”的暂停与恢复，这是 P2 选型的考察项之一。

### A5 没有数据安全限制（2026-11-06 确认）

- 实验室资料可以发送给外部模型 API，不需要本地部署模型。
- 模型供应商的选择（D2）只需考虑效果和成本。

### A6 不允许运行中自我修改（已确认）

- Agent 不能在运行中修改自己的提示词或技能。
- 改进走离线循环：出错 → 按 trace 定位 → 提出修改 → 用基准任务包回归 → 人工批准 → 发布新版本。

### A7 人工确认点（已确认）

| 环节 | 要求 |
|---|---|
| 需求基线 | 由人确认后才开始规划 |
| 方案采纳 | 由人确认 |
| 对外动作（询价、下单、发邮件） | 由人批准，Agent 只起草 |
| 规划中的歧义 | Copilot 可以暂停提问（A4） |

## 3. 已有方向、待细化

### B1 上下文（Context）

| 角色 | 能看到的 | 看不到的 |
|---|---|---|
| Copilot | 需求、各 Artifact 的结论摘要、未解决的缺口、项目历史摘要 | Specialist 的搜索过程和原始网页 |
| Specialist | 自己的 Brief、相关需求项、自己的技能、本次工具结果 | 其他 Specialist 的工作、整个项目的历史 |

- 长内容（PDF、整页参数）不直接放进上下文，先存为文件或证据，上下文中只放摘要和引用编号，需要时再读取。

### B2 技能（Skills）

- 技能 = 操作说明 + 确定性工具 + 测试用例。
- 带版本号；每个 Specialist 只能使用分配给它的技能。
- Artifact 记录所用技能的版本。

## 4. 待讨论

### C1 trace 的详细程度

已知的事实：

- **记录 trace 本身不消耗模型 token。** trace 只是把每次调用的输入、输出、耗时、token 数写进数据库，和写日志一样，花费的是存储空间，不是模型费用。
- 只有两种情况会因 trace 消耗 token：
  1. 用模型去**分析** trace，例如自进化循环里让模型总结失败原因。
  2. 把历史 trace 放回 Agent 的上下文。按 B1 的设计，不会这样做。

待决定：

- 是完整保存每次模型调用的输入和输出，还是只保存摘要？
- 保留多久？是否设置“N 天后只保留摘要”？
- 用什么格式：OpenTelemetry GenAI 规范，还是底座自带的格式？
- 在哪里看：P3 的查看页面，还是引入 Langfuse 之类的专门工具？

不论最终怎么选，**业务记录与 trace 之间的连接字段（运行 ID 等）都在 P1 预留**，见 P1 任务说明 3.8 节。
